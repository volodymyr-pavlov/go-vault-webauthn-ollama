# The threat model

The attacker can phish users, hold a copy of the database, hold a leaked Vault token or a stolen device key and control any text that a user
submits. The network is hostile, and TLS ends at a reverse proxy.

Each row names the threat, what the service does about it, the test that covers it and the risk that remains.

| Threat | Mitigation | Test | Residual risk |
| --- | --- | --- | --- |
| Phishing and relay of credentials | Passkeys are bound to the origin and the RP ID. The browser enforces this and the server checks it. An account with a passkey accepts no password or code, so a phished password is useless. | `auth.TestLoginRefusals` (wrong origin, wrong RP ID), `server.TestNoDowngrade` | Accounts that still use a password and TOTP can be phished until they enroll a passkey. A real-time proxy can relay a TOTP code within its time step. |
| Replay of a ceremony | The challenge lives on the session that began the ceremony. The statement that accepts it also clears it. It expires in two minutes and names its ceremony type. | `server.TestPasskeyRefusals` (replay, expired), `mysql.TestSessionLifecycle` (consumed once) | None known. |
| A cloned authenticator | The counter rule: if both counters are zero, the service accepts the login (synced passkeys). Otherwise, a counter that does not grow disables the passkey, refuses the login and sends a notice to the user. | `auth.TestCounterRule`, `server.TestCounterRule` | A clone of a synced passkey reports zero like the original, so the counter cannot detect it. Only the new-device signal of the risk engine remains. |
| TOTP brute force and replay | A code has six digits and a window of one step. The service stores the last accepted step and never accepts it again. The comparison takes the same time for every input. Each account has a budget in Redis with a growing delay, and the service counts failures on the account and on the session. | `totp.TestWindowAndReuse`, `server.TestPasswordAndTOTPLifecycle`, `api.TestRateLimitByAddress` | A code is valid for up to 90 seconds. The budget slows a distributed attempt, but a large botnet gets more tries than a single address. |
| Factor downgrade | The handlers hold the policy. An account with a passkey, even a disabled one, has no password path. | `server.TestNoDowngrade` | None known. |
| Takeover through adding a factor or through enrollment | Adding or removing a factor needs the last factor within five minutes. Enrollment after registration or recovery needs the verification token or a recovery code. Every change sends a notice to the user. | `server.TestFreshAuthentication`, `server.TestRecovery` | A notice in Mailpit reaches nobody. In production, the notice must go through a channel that the attacker does not control. |
| Database theft | Passwords are Argon2id hashes. TOTP secrets are Transit ciphertexts bound to the user. Recovery codes and device identifiers are keyed or 256-bit hashes. The WebAuthn keys and the device keys are public keys and are useless without the private keys. | `server.TestTOTPCiphertextMovedBetweenUsers`, `vaulttest.TestContextBindsCiphertext` | An attacker can read the emails and the login history. An attacker who also has the Vault token can decrypt through Vault. See the next row. |
| Vault token theft | The AppRole token lives for fifteen minutes and the service renews it. Its policy has four paths: encrypt, decrypt and rewrap with the TOTP key, and HMAC with the MAC key. No path returns key material. The service gets the secret ID wrapped, and the unwrap works only once. | `vault.TestTransitWithRealVault` (policy denials, second unwrap fails) | While it lives, a stolen token decrypts any ciphertext that it receives. The audit device of Vault is what catches this. |
| A Vault outage | Operations that need Vault fail closed: no TOTP check, no enrollment and no recovery code. The check of a request signature does not use Vault, so an outage does not affect it. If the login to Vault fails, the service keeps running, tries again with a growing delay (1 to 30 seconds), and fails closed until it has a token. | `auth.TestRequestVerifier` (the verifier has no Vault client), `server.TestFaultVaultDown`, `vault.TestLoginAgainSurvivesAShortOutage` | The design trades availability for security. A second Vault node is the production answer. |
| A stolen or replayed request | The signature covers the method, the path and the digest of the body, so nobody can change a request or move it. The time must be within one minute of the server time. A nonce works once for each key (Redis `SETNX`, two minutes), so the service refuses a captured request when it arrives again. It also refuses a request with a query string. | `auth.TestRequestVerifier` (stale, changed, same nonce again), `server.TestRequestSignature`, `server.TestFaultReplayedRequest` (one nonce sent 20 times at once), `server.TestFaultRedisDown` | If an attacker captures a request and sends it before the client does, it works once. If Redis is down, requests fail and do not pass. |
| Session theft by an adversary in the middle after login | There is no token to steal. The browser generates the key and does not let anyone export it, and only the public key leaves the browser. Every request needs a new signature with a one-time nonce, so a stolen request is useless on another device. The service reads the session row on every request, and the Revoked flag ends the session at once. The headers tell the browser to use HTTPS only and never to cache. The origin check refuses cross-site requests. Every request names its session in the signed `tag`, and the key ID must belong to that session. An idle session ends after `-session-idle`, and the user can end any session from the Devices panel. | `auth.TestRequestVerifier`, `auth.TestKeyIDIsTheHashOfTheKey`, `server.TestRequestSignature`, `server.TestPasskeyRefusals`, `server.TestSessionsOfOneKey`, `server.TestIdleSessionEnds`, `server.TestDevicesList` | Code that runs on the page can still ask the browser to sign while the page is open. A browser that blocks IndexedDB keeps the key for that page only. |
| Account enumeration | Registration, the start of a passkey login and the start of a recovery answer the same way for a known and an unknown address, and they cost the same work. The login options list credentials that a keyed hash of the address produces. | `server.TestUniformResponses` | The database read differs by a few microseconds. The Argon2 work hides this. |
| Abuse of account recovery | A recovery code has 80 bits, works once and is stored as a Vault HMAC. Using a code binds the session to the account for enrollment only. It never logs the user in, it sends a notice to the user and it logs an event. | `server.TestRecovery` | A user who lost every factor and every code needs the request flow in the next rows. |
| A thief starts recovery for an account | The request only starts a delay (72 hours by default). The owner receives a notice with a single-use cancel token. A login with any factor, or a recovery code, cancels the request. After the delay, an operator must check the owner and approve the request, and the command refuses to approve earlier. Then the service emails a single-use grant token that is valid for one hour. Using the grant revokes every other session and allows enrollment only. The request and the claim answer 202 for any email. | `server.TestRecoveryOfLostFactors`, `server.TestRecoveryGrantExpires`, `server.TestLoginCancelsRecovery` | The operator check happens outside the code, and a weak check defeats the flow. A thief who also reads the mail of the owner sees the notice and the grant. |
| Removing a factor with a stolen session | Removing a passkey needs a fresh passkey assertion. The challenge is the SHA-256 hash of a domain string, 32 random bytes, the action and the passkey. The state holds the same action and passkey. The challenge works once and for two minutes, and a refusal uses it up. | `auth.TestConfirmationAcceptsOnlyItsActionAndTarget`, `server.TestConfirmedRemovalIsBoundToItsPasskeyAndWorksOnce`, `server.TestFreshAuthentication` | A person who holds the unlocked authenticator of the owner can still confirm. Other sensitive changes need only a fresh login. |
| Account takeover through the email | The email alone gives no access. The notice and the grant both go to the mailbox, so the delay, the human approval and the cancel by a login are the defence. No second channel exists yet. | `server.TestRecoveryOfLostFactors`, `server.TestLoginCancelsRecovery` | If the attacker controls the mailbox and passes the operator check, the account is lost. A second channel, such as a push message to a logged-in device, is not built. |
| Leakage through logs | The log lines and rows of the request log carry identifiers, statuses and coarse values. A log line shows only the network of the address (/24 for IPv4, /48 for IPv6), and an hourly job deletes the rows after `-request-log-retention`. The service never logs a body, a header, a token, a code or a credential. The cause of a failure goes to the error log of the mux without the request. | `api.RequestLog` by construction, `server.TestMetrics` (limited labels), `server.TestRequestLogRecordsEveryRequestWithoutItsBody`, `api.TestLogAddressClearsTheHostPart`, `mysql.TestPurgeHTTPRequestsDeletesOnlyTheOldRows`. The email is the one place where a token is written, on purpose. | The stand emails the verification tokens to Mailpit. Production sends real email. |
| Prompt injection and manipulation of the model | The prompt is a fixed template of typed, coarse fields. No string that a user typed reaches it. A JSON schema constrains the response and the service checks it strictly. The model can raise a decision by one step only. | `ai.TestHostileOutput`, `ai.TestHostileOutputCannotLowerRisk`, `server.TestAdvisorOnlyRaises`, `FuzzParseAdvice`, `server.TestFaultOllamaFailures` (slow or hostile Ollama) | A model that always says "high" would limit every login. The review flag and the logs show this. |
| Sensitive data sent to the model | The summary holds a keyed pseudonym, a country, a four-hour bucket, the factor and the signals. It holds no email, no address and no name. | `ai.TestAdviseParsesAndMinimizes`, `server.TestAdvisorOnlyRaises` | The model runs on the internal network of the stand, on the same machine. |
| Forcing victims into extra verification through the risk engine | Failures of other accounts from the same address raise the score by at most 25 points, and a shared address (5 accounts in an hour) adds 10. Together they reach the medium band, which limits the login and does not refuse it. Nothing that an attacker does to another account denies it. It only slows it. | `ai.TestScoreAndLevel`, `server.TestSharedAddressSignal` | A victim who shares an address with an attacker is limited more often. With a new device at an odd hour, the victim can be refused. An office or a mobile carrier sets the shared-address signal for honest users. |
| An exposed Ollama port | Ollama has no published port and sits on an internal network. The client checks the digest of the model at start-up, limits the request size, the concurrency and the time, and opens a breaker after failures. | `ai.TestCheckDigest`, `ai.TestTimeoutOpensBreaker`, `ai.TestConcurrencyCap` | Anything on the same internal network can talk to Ollama. |
| Flooding with sessions | Redis limits opening a session to 20 a minute for each address. The other limits stay: 60 requests a minute for each address, 20 a minute for each account and 500 a second for the service. The service deletes expired sessions after `-session-retention`. | `server.TestSessionOpenLimit`, `server.TestPurgeExpiredSessions`, `api.TestRateLimitByAddress` | A botnet with many addresses gets many sessions. |
| A wrong clock or a shifted time window | A time outside one minute gives 401 `STALE_REQUEST_TIME` with the server time, and the page tries once more with an offset. The nonce check still holds. | `server.TestStaleRequestTimeCarriesServerTime` | Nobody authenticates the server time, so an attacker in the middle can move the offset. Each request is still signed and works once. |
| A mail channel in clear text | `-smtp-starttls` or `-smtp-implicit-tls` turns on TLS (1.2 or newer, system roots, no skipped checks). The client never sends AUTH PLAIN without TLS. | `smtp.TestStartTLSSendsOverTrustedCertificate` | The default is plain SMTP, only for local stands. The operator chooses the mail provider. |
| Approval of a recovery request before the delay ends | The `recovery` command lists and approves requests. The approval fails before the delay ends. | `cmd/recovery` `TestApproveRespectsDelay`, `TestListStates`, `mysql.TestRecoveryRequestApproveNeedsDelay` | The operator check happens outside the code. |
| Personal data kept after a deletion request | `DELETE` runs in one transaction: it deletes the user, the passkeys, the recovery codes, the recovery requests and the sessions, and it removes the user, the address and the user agent from the request log rows of the user. The row of the deletion itself carries no identity. The export lists the same data on request. | `server.TestAccountExportAndDeletionWithAPasskey`, `server.TestAccountDeletionWithoutAPasskeyNeedsAFreshLogin`, `server.TestParallelConfirmationsWorkOnce`, `mysql.TestDeleteAccountRunsEveryDeleteInOrder` | A request that was in flight during the deletion writes its log row afterwards, with the old user number and the address. The retention job deletes it within `-request-log-retention`. The email in the notice of the deletion is the only copy that the service sends out. |
| A vulnerable dependency | `govulncheck` runs in `make verify` and in CI. The base images and the actions are pinned by digest. | CI | A vulnerability that someone publishes between two runs. |
